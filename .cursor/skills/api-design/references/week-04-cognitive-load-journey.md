# Неделя 04 — Usability, task journey и когнитивная нагрузка

## Контекст

Usability API — управление когнитивной работой потребителя. Удобство **must not** сводить к числу методов или длине fluent chain.

**Must оценивать:** полный task journey, не изолированную сигнатуру.

## Task journey — единица review

```text
намерение → поиск точки входа → конфигурация → вызов → обратная связь → диагностика → исправление
```

API удобен, если на каждом этапе достаточно сигналов для правильного следующего шага.

## Три измерения usability

| Измерение | Вопрос для API |
|---|---|
| Результативность | Задача выполняется корректно? |
| Эффективность | Сколько усилий, решений, итераций? |
| Удовлетворённость | Предсказуемость и доверие (не «красота») |

**Must:** удовлетворённость = контроль: потребитель понимает, почему система выбрала поведение, и может воспроизвести результат.

## Локальная vs системная usability

**Must review:** когнитивная стоимость переходов между поверхностями:

- Java API ↔ configuration
- configuration ↔ effective runtime state
- runtime ↔ operational signals
- exception ↔ remediation
- deprecated API ↔ migration path

**Must not:** один термин в Java, другой в YAML, третий в metrics, четвёртый в Actuator без явной связи.

## Три вида когнитивной нагрузки

| Вид | Источник | Задача дизайнера |
|---|---|---|
| Intrinsic | объективная сложность домена | представить честно и структурированно |
| Extraneous | случайная сложность формы | устранить лишние решения, скрытые правила |
| Germane | построение полезной схемы | устойчивая ментальная модель, перенос знаний |

**Must not:** скрывать intrinsic complexity за `manager.process(config)` — extraneous load растёт без словаря и точек контроля.

## Lifecycle использования (must учитывать все)

- первое подключение
- типовая разработка
- редкая настройка
- тестирование
- диагностика production failure
- обновление версии
- удаление/замена библиотеки

**Must not:** оптимизировать только time-to-first-success → onboarding-friendly, operations-hostile API.

## Ментальная модель

**Must:** направлять потребителя к модели, достаточной для правильных решений, без изучения внутреннего алгоритма.

**Must not:** объединять policy, schedule, budget, result в один `RetryHandler` без границ; публиковать 15 стратегий без общей структуры.

## Consistency (снижает перенос)

| Тип | Must |
|---|---|
| Терминологическая | одно понятие — одно имя |
| Структурная | похожие задачи — похожая форма |
| Поведенческая | одинаковые операции — одинаковые эффекты |
| Временная | lifecycle patterns повторяются |
| Диагностическая | ошибки и remediation единообразны |
| Межповерхностная | Java, YAML, metrics, docs — общий словарь |

## Principle of least surprise

**Must:** соответствовать ожиданиям целевой аудитории Java: `get` не запускает сеть; `close` освобождает ресурс; immutable value — стабильная equality.

**Must:** при нарушении convention — заметно через тип, имя или документацию.

## Decision count — основная метрика

Для task journey **must выпишите** decision points:

- обязательно или есть безопасный default?
- есть ли информация в момент выбора?
- варианты взаимоисключающие и сопоставимые?
- последствие локально или глобально?
- можно ли изменить позже?
- диагностируется ли неверный выбор?

**Must not:** считать строки кода вместо решений.

## Сильный default

Default **must:**

- быть безопасным для большинства
- стабильным между средами
- наблюдаемым после запуска
- не блокировать явную настройку
- иметь documented rationale
- не меняться в minor без compatibility analysis

**Must not:** default от случайного classpath — скрытое решение системы.

## Progressive disclosure

Три уровня **must** описывать **одну модель**:

1. convention/default для типового сценария
2. явные policy objects для вариаций
3. SPI / low-level hooks для специализации

**Must not:** high-level `RetryPolicy` + low-level `AttemptContextImpl` без связи — два несвязанных API.

### Escape hatch

**Must:** доменная настройка → узкий SPI → явно version-coupled low-level integration.

**Must not:** `customizer(Consumer<InternalSdkBuilder>)` как первый recommended path — публикует compatibility contract на internals.

## Key theses

1. Пользователь выполняет задачу, не вызывает метод.
2. Usability = результативность + эффективность + предсказуемость пути.
3. Intrinsic complexity нельзя убрать; extraneous — must устранять.
4. Consistency снижает стоимость переноса между поверхностями.
5. Число решений важнее числа строк.
6. Default — принятое за пользователя решение и часть compatibility contract.
